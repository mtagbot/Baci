  راهنمای بروزرسانی نسخهٔ ۴.۱۳۱.۰  (نسخهٔ دسکتاپ: ۲.۶۲.۰)
════════════════════════════════════════════════════════════════════

این نسخه شش مورد از بازبینی امنیتی/کارایی را رفع می‌کند. مهم‌ترینش
مورد اول است: تا پیش از این، کد ملی دانش‌آموز عملاً رمز عبور معتبر بود.

هیچ تغییر دیتابیسی دستی لازم نیست. ایندکس‌های جدید خودکار ساخته
می‌شوند (توضیح در بخش ۲).


────────────────────────────────────────────────────────────────────
۱) ورود با رمز خام حذف شد   ← امنیتی، مهم‌ترین مورد
────────────────────────────────────────────────────────────────────
مشکل چه بود
-----------
همهٔ مسیرهای ورود این شکل بودند:

    password_verify($pass, $row['password'])
        || $pass === $row['password']          ← رمز خام
        || $pass === $row['personnel_code']    ← دبیر
        || $pass === $row['national_id']       ← دانش‌آموز

یعنی اگر رمز واقعی را هم نمی‌دانستید، کد ملی کافی بود. و کد ملی در
همین سامانه «نام کاربری» است — پس آن حساب‌ها در عمل بی‌رمز بودند.
برای دبیران هم کد پرسنلی همین نقش را داشت.

چه شد
-----
یک تابع واحد به includes/functions.php اضافه شد:

    verify_user_password($plain, $stored, ['table'=>..,'id'=>..])

فقط هش را می‌پذیرد. کد ملی و کد پرسنلی دیگر هرگز رمز نیستند.

حساب‌های قدیمی قفل نمی‌شوند: اگر رمز ذخیره‌شده هنوز خام است و کاربر
دقیقاً همان را وارد کند، یک‌بار وارد می‌شود و همان لحظه رمزش به هش
تبدیل و در دیتابیس نوشته می‌شود. یعنی مهاجرت خودش انجام می‌شود و بعد
از اولین ورود هر کاربر، دیگر هیچ رمز خامی در جدول نمی‌ماند.

۱۵ نقطه در ۶ فایل اصلاح شد:
  admin-login.php (۲ مورد) · index.php (۴ مورد) · api/index.php (۲)
  profile.php (۲) · my-sessions.php (۳) · bot_webhook_engine.php (۴)

دو مورد عمداً دست‌نخورده ماند و دلیلش در کد نوشته شده است: در «اتصال
حساب به ربات»، کد پرسنلی دبیر و شمارهٔ سریال دانش‌آموز نقش عامل
شناسایی را دارند نه رمز عبور. فقط مقایسه با ستون خام password از
آن‌ها هم برداشته شد.

  ⚠ بعد از نصب، به کاربرانی که تا امروز با «کد ملی» وارد می‌شدند
    بگویید از رمز واقعی‌شان استفاده کنند. اگر رمزی تنظیم نشده،
    از پنل مدیریت برایشان رمز بگذارید.


────────────────────────────────────────────────────────────────────
۲) ایندکس‌های کارایی   ← سرعت، مخصوصاً نسخهٔ دسکتاپ
────────────────────────────────────────────────────────────────────
sql/database.sql (نسخهٔ MySQL) ۱۱۳ تعریف KEY داشت، ولی
sql/schema-sqlite.sql (نسخهٔ دسکتاپ) فقط ۱ ایندکس. یعنی روی دسکتاپ
کوئری‌هایی مثل «کارنامه‌های این دانش‌آموز» کل جدول را می‌خواندند.

۵۸ ایندکس اضافه شد که مستقیماً از همان تعاریف KEY فایل MySQL تولید
شده‌اند (به‌علاوهٔ چند مسیر داغ مخصوص دسکتاپ: حضورغیاب و کارنامه).

اندازه‌گیری واقعی (SQLite، ۱۲۰٬۰۰۰ ردیف، ۳۰۰ کوئری):
    بدون ایندکس ۵٫۳۶ms  →  با ایندکس ۰٫۱۲ms   (~۴۳ برابر)

نصب خودکار است: همهٔ ایندکس‌ها IF NOT EXISTS هستند و
includes/db.php::ensureSchemaCurrent() بعد از هر ارتقا فایل schema را
دوباره اجرا می‌کند. پس روی دیتابیس موجودِ شما هم ساخته می‌شوند، بدون
اینکه کاری بکنید و بدون خطر برای داده‌ها.

روی سایت (MySQL): ۵۴ تا از این ۵۸ از قبل موجود بودند. ۴ مورد باقی‌مانده
را با دکمهٔ «اعمال ایندکس‌های حیاتی» در صفحهٔ «سلامت پایگاه داده»
اضافه کنید (یک‌بار، چند ثانیه).


────────────────────────────────────────────────────────────────────
۳) صفحهٔ «سلامت پایگاه داده» روی دسکتاپ کار افتاد
────────────────────────────────────────────────────────────────────
db-optimizer.php تماماً با information_schema و «ALTER TABLE ADD
INDEX» و «OPTIMIZE TABLE» نوشته شده بود — هیچ‌کدام در SQLite وجود
ندارند. ولی منو این صفحه را روی دسکتاپ هم نشان می‌داد، پس کاربر
دکمه‌هایی می‌دید که بی‌صدا شکست می‌خوردند (خطاها در try/catch بلعیده
می‌شدند). بدتر: چون dbopt_index_exists() در catch مقدار true
برمی‌گرداند، همه‌چیز «از قبل موجود» گزارش می‌شد.

حالا صفحه هر دو موتور را می‌شناسد:
    MySQL  → information_schema · ADD INDEX · ANALYZE/OPTIMIZE TABLE
    SQLite → sqlite_master/PRAGMA · CREATE INDEX · ANALYZE · VACUUM

ضمناً دو ناسازگاری دیگر هم رفع شد:
  • ده کوئری «DELETE alias FROM ... LEFT JOIN» که فقط MySQL می‌فهمد،
    به شکل قابل‌حمل (زیرکوئری NOT IN) بازنویسی شدند.
  • عملگر <=> مخصوص MySQL به لایهٔ ترجمهٔ SQLite اضافه شد (معادلش
    آنجا IS است). این عملگر در بخش «حذف تکراری‌ها» استفاده می‌شد و
    روی دسکتاپ خطای نحوی می‌داد.

جدول حجم جداول هم برای SQLite بازنویسی شد: تعداد ردیف دقیق شمرده
می‌شود و حجم کل فایل + فضای آزاد قابل بازپس‌گیری با VACUUM نمایش
داده می‌شود.


────────────────────────────────────────────────────────────────────
۴) آپلود رسانهٔ سوال سخت‌سازی شد
────────────────────────────────────────────────────────────────────
online-exam-media-upload.php تنها لاگین‌بودن و پسوند را چک می‌کرد. نه
CSRF داشت، نه سقف حجم، نه بررسی محتوای واقعی فایل.

اضافه شد:
  ۱) توکن CSRF
  ۲) سقف ۱۰ مگابایت + مدیریت خطاهای خود PHP
  ۳) بررسی MIME واقعی با finfo (نه فقط پسوند)
  ۴) تطابق اجباری «پسوند ↔ MIME» تا فایل .jpg حاوی PHP رد شود
  ۵) نام فایل کاملاً تصادفی (پیش‌تر با time() قابل حدس بود)
  ۶) نوشتن .htaccess در پوشهٔ مقصد

درخواست HEAD عمداً باز ماند چون صفحهٔ آزمون دانش‌آموز از آن برای
سنجش سرعت اینترنت استفاده می‌کند.

  ⚠ اگر online-exam-questions.php را جایگزین نکنید، آپلود تصویر در
    استودیوی سوال کار نخواهد کرد (توکن CSRF از همان‌جا فرستاده
    می‌شود). این دو فایل باید با هم نصب شوند.


────────────────────────────────────────────────────────────────────
۵) پوشه‌های uploads و backups محافظت شدند
────────────────────────────────────────────────────────────────────
در کل پروژه هیچ فایل .htaccess وجود نداشت. روی هاست اشتراکی Apache،
هر فایلی که در uploads/ بنشیند و به PHP تفسیر شود اجرا می‌شود — با
مورد ۴ ترکیب شود، زنجیرهٔ «آپلود → اجرای کد» کامل است.

  uploads/.htaccess  → اجرای PHP خاموش، هندلرها برداشته، لیست پوشه off
  backups/.htaccess  → دسترسی مستقیم کاملاً ممنوع

پوشهٔ backups مهم‌تر است: محتوایش dump کامل دیتابیس است (مشخصات
دانش‌آموزان، نمرات، هش رمزها). دانلود مستقیم یکی از آن فایل‌ها یعنی
افشای کل مدرسه.

  ⚠ اگر روی Nginx هستید، .htaccess خوانده نمی‌شود. معادلش را در
    کانفیگ سرور بگذارید:
        location ^~ /uploads/ { location ~ \.php$ { return 403; } }
        location ^~ /backups/ { deny all; }


────────────────────────────────────────────────────────────────────
۶) حذف آزمون آنلاین دیگر رکورد یتیم نمی‌گذارد
────────────────────────────────────────────────────────────────────
تا اینجا حذف آزمون فقط online_exams و online_questions را پاک می‌کرد.
شرکت‌کننده‌ها، پاسخ‌ها، لاگ‌های نظارت، سشن‌های زنده، اسنپ‌شات‌های وب‌کم
و فایل‌های آپلودیِ دانش‌آموزان تا ابد در دیتابیس و روی دیسک می‌ماندند.

حالا برای هر شرکت‌کننده از همان تابع online_exam_delete_attempt_full()
استفاده می‌شود که در v4.125.0 نوشته شده بود — هم رکوردها و هم فایل‌ها
را برمی‌دارد و مسیرها را در برابر traversal می‌سنجد. رسانهٔ مشترک
سوالات عمداً دست‌نخورده می‌ماند چون به سوال تعلق دارد نه به دانش‌آموز.

پیام موفقیت حالا تعداد شرکت‌کننده و فایل حذف‌شده را هم می‌گوید.


────────────────────────────────────────────────────────────────────
+ اجرای خودکار تست (CI)
────────────────────────────────────────────────────────────────────
.github/workflows/tests.yml اضافه شد: روی هر push و هر PR، همهٔ
سوئیت‌ها از یک کلون تمیز و روی بستهٔ منتشرشده اجرا می‌شوند.

چرا لازم بود: دو سوئیت (تختهٔ سفید و مانیتورینگ) مسیر سورس را به
پوشهٔ محلی .arena/current سیم‌کشی کرده بودند و روی کلون تازه اصلاً
اجرا نمی‌شدند — ماه‌ها «سبز» بودند بدون اینکه چیزی را بسنجند. رفع شد
و CI دقیقاً همین دسته باگ را می‌گیرد.
